Ik heb een uitdagende databaseopdracht voor je bedacht op gevorderd niveau. Deze opdracht combineert databaseontwerp, SQL, relationele verbanden, normalisatie en website-integratie.
Opdracht: Ontwikkel een compleet reserverings- en boekingsplatform

Gevorderd niveau Database + SQL + Website
1. De situatie

Je gaat een database ontwikkelen voor een fictief bedrijf genaamd Eventify.

Eventify is een online platform waarop gebruikers evenementen kunnen bekijken, tickets kunnen kopen, betalingen kunnen uitvoeren en hun bestellingen kunnen beheren.

De database moet uiteindelijk gekoppeld worden aan een website waarop bezoekers:

    Een account kunnen aanmaken.

    Evenementen kunnen bekijken.

    Evenementen kunnen filteren op categorie, locatie en datum.

    Tickets kunnen bestellen.

    Online betalingen kunnen uitvoeren.

    Hun bestellingen kunnen bekijken.

    Reviews kunnen achterlaten.

Daarnaast moet een beheerder evenementen, gebruikers, tickets en bestellingen kunnen beheren.

3. Relaties tussen de tabellen

Je moet gebruikmaken van verschillende soorten relaties:

    One-to-One: bijvoorbeeld een gebruiker en zijn profiel.

    One-to-Many: één organisator kan meerdere evenementen organiseren.

    Many-to-Many: één evenement kan meerdere categorieën hebben en één categorie kan bij meerdere evenementen horen.

Een voorbeeld van de databaseopbouw:
How to Design ER Diagrams for Online Ticketing and Event Management - GeeksforGeeks
 

De relaties moeten correct worden geïmplementeerd met:

    Primary Keys (PK).

    Foreign Keys (FK).

    Unique constraints.

    Check constraints.

    Indexes.

4. Functionele eisen

Je database moet de volgende functionaliteiten ondersteunen.

Gebruikers

    Gebruikers registreren.

    Gebruikers aanpassen en verwijderen.

    Verschillende gebruikersrollen beheren.

    Gebruikers blokkeren.

Evenementen

    Evenementen toevoegen, aanpassen en verwijderen.

    Evenementen koppelen aan organisatoren.

    Evenementen koppelen aan meerdere categorieën.

    Evenementen filteren op datum, locatie en categorie.

Tickets en bestellingen

    Verschillende ticketsoorten per evenement.

    Meerdere tickets in één bestelling.

    Automatisch de totaalprijs berekenen.

    Bijhouden hoeveel tickets nog beschikbaar zijn.

    Voorkomen dat meer tickets worden verkocht dan beschikbaar.

Betalingen

    Betalingen registreren.

    Betaalstatus bijhouden.

    Meerdere betaalpogingen kunnen registreren.

    Terugbetalingen ondersteunen.

Reviews

    Gebruikers kunnen evenementen beoordelen.

    Een gebruiker mag een evenement maximaal één keer beoordelen.

    Reviews moeten een score van 1 tot 5 bevatten.

5. Geavanceerde SQL-opdrachten

Hier begint de echte uitdaging. Je moet minimaal de volgende SQL-query's ontwikkelen.

    Toon alle evenementen met hun organisator en locatie.

    Toon alle evenementen met meer dan 100 verkochte tickets.

    Bereken de totale omzet per evenement.

    Toon de vijf populairste evenementen.

    Toon alle gebruikers die nog nooit een bestelling hebben geplaatst.

    Bereken de gemiddelde beoordeling per evenement.

    Toon alle bestellingen van een specifieke gebruiker.

    Toon alle evenementen waarvan de tickets bijna uitverkocht zijn.

    Bereken de totale omzet per organisator.

    Toon de gebruikers die het meeste geld hebben uitgegeven.

Extra uitdagingen:

    Maak minimaal twee SQL Views.

    Maak minimaal twee Stored Procedures.

    Maak minimaal twee Triggers.

    Maak gebruik van transacties (COMMIT en ROLLBACK).

    Implementeer indexes voor betere prestaties.

    Zorg voor databasebeveiliging en correcte toegangsrechten.

Je levert uiteindelijk het volgende op:

    Een volledig ERD-diagram.

    Een SQL-bestand waarmee de volledige database aangemaakt wordt.

    Een SQL-bestand met testgegevens.

8. Extra moeilijke uitdagingen

Wil je het jezelf echt moeilijk maken? Voeg dan deze uitdagingen toe:

    Een ticketsysteem met tijdelijke reserveringen.
    Automatische vrijgave van niet-betaalde reserveringen.
    Een kortingscodesysteem.
    Een wachtlijst voor uitverkochte evenementen.
    Een auditlog waarin alle belangrijke wijzigingen worden opgeslagen.
    Een dashboard met statistieken over omzet en bezoekers.
    Een API waarmee externe applicaties evenementen kunnen ophalen.
    Een systeem met verschillende toegangsrechten voor beheerders en organisatoren.

Mijn advies: maak het project zo

Bouw het niet alleen als een databaseopdracht, maar als een echt softwareproject.

De moeilijkheid zit vooral in:

    Het goed ontwerpen van de relaties.

    Het voorkomen van dubbele of inconsistente gegevens.

    Het correct verwerken van bestellingen en betalingen.

    Het voorkomen van dubbele ticketverkoop bij gelijktijdige bestellingen.

    Het efficiënt ophalen van gegevens voor de website.

Extra uitdaging: ontwerp eerst de volledige database zonder website te bouwen. Zorg dat alle relaties, constraints en query's werken. Bouw daarna pas de website en koppel deze aan je database.

Zo heb je een serieus project waarmee je je SQL- en databasevaardigheden op gevorderd niveau kunt testen.

Het belangrijkste om te onthouden:

    AUTO_INCREMENT gebruik je voor ID-kolommen die automatisch een nieuw nummer krijgen.

    PRIMARY KEY identificeert een record uniek.

    FOREIGN KEY verwijst naar een bestaande rij in een andere tabel.

    UNIQUE voorkomt dubbele waarden.

Voorbeeld van een correcte ID-kolom:
sql

user_id INT NOT NULL AUTO_INCREMENT,
PRIMARY KEY (user_id)

Voorbeeld van een correcte foreign key-kolom:
sql

user_id INT NOT NULL,
FOREIGN KEY (user_id) REFERENCES Users(user_id)

Een foreign key krijgt dus normaal gesproken geen AUTO_INCREMENT.
2. Aanpassingen per tabel

Hieronder staan de concrete wijzigingen die ik zou doorvoeren.
1. categories

Je hebt:
sql

category_name VARCHAR(50) NULL DEFAULT (UNIQUE)

Dit is fout. UNIQUE is geen defaultwaarde.

Maak ervan:
sql

category_name VARCHAR(50) NOT NULL UNIQUE

Ik zou ook category_id automatisch laten oplopen:
sql

category_id INT NOT NULL AUTO_INCREMENT

2. event_categories

Je hebt momenteel geen primary key. Bovendien is AUTO_INCREMENT verkeerd gebruikt.

Vervang de tabel door:
sql

CREATE TABLE event_categories
(
    event_category_id INT NOT NULL AUTO_INCREMENT,
    event_id INT NOT NULL,
    category_id INT NOT NULL,

    PRIMARY KEY (event_category_id),
    UNIQUE (event_id, category_id)
);

De extra UNIQUE voorkomt dat je dezelfde categorie twee keer aan hetzelfde evenement koppelt.
3. events

Hier zitten drie belangrijke fouten.

Je hebt:
sql

organizer_id INT NOT NULL DEFAULT (AUTO_INCREMENT),
location_id INT NOT NULL DEFAULT (AUTO_INCREMENT),
created_at VARCHAR(255) NULL

Dit moet worden:
sql

event_id INT NOT NULL AUTO_INCREMENT,
organizer_id INT NOT NULL,
location_id INT NOT NULL,
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP

Waarom?

    event_id is de unieke identificatie van het evenement.

    organizer_id verwijst naar een organisator.

    location_id verwijst naar een locatie.

    created_at slaat een datum en tijd op, geen tekst.

location_id INT NOT NULL AUTO_INCREMENT

3. Ontbrekende verbeteringen in je database

Naast de SQL-fouten zijn er nog een paar zaken die je database professioneler maken.

Verbetering
	

Waarom?

ON DELETE RESTRICT
	

Voorkomt dat je records verwijdert waar nog afhankelijkheden van bestaan

ON UPDATE CASCADE
	

Houdt gekoppelde sleutels consistent bij wijzigingen

Index op foreign keys
	

Verbetert prestaties bij JOIN-query's

DEFAULT CURRENT_TIMESTAMP
	

Registreert automatisch wanneer een record is aangemaakt

ENGINE=InnoDB
	

Ondersteunt foreign keys en transacties

Je kunt bijvoorbeeld een foreign key als volgt schrijven:
sql

ALTER TABLE events
ADD CONSTRAINT FK_organizers_TO_events
FOREIGN KEY (organizer_id)
REFERENCES organizers (organizer_id)
ON UPDATE CASCADE
ON DELETE RESTRICT;

Let op: als je deze wijziging toepast, moet je de bestaande foreign key eerst verwijderen.

5. Wat ik nog zou verbeteren

Er is één belangrijk databaseprobleem dat je nog niet hebt opgelost: de consistentie van bestellingen.

Bijvoorbeeld:

    Een gebruiker bestelt 2 tickets.

    De bestelling wordt betaald.

    De betaling wordt geregistreerd.

    De ticketvoorraad wordt verlaagd.

Dit moet als één veilige database-transactie gebeuren. Anders kunnen er verkeerde aantallen ontstaan wanneer twee gebruikers tegelijkertijd tickets bestellen.

Dat is een mooie volgende stap voor jouw gevorderde databaseproject.

Mijn advies: vervang eerst de 14 tabeldefinities hierboven en voer daarna je ALTER TABLE-statements uit. Dan heb je een veel betere technische basis voor Eventify.

4. Eén belangrijk probleem met je relaties

Je hebt bijvoorbeeld deze relatie:
sql

ALTER TABLE events
ADD CONSTRAINT FK_organizers_TO_events
FOREIGN KEY (organizer_id)
REFERENCES organizers (organizer_id);

Deze is correct.

Maar let op: je moet eerst de tabel organizers aanmaken voordat je de foreign key toevoegt.

Je doet dat in je script goed: eerst maak je alle tabellen en daarna voeg je de foreign keys toe.
5. Mijn advies: doe nog deze extra verbeteringen

Om je database echt op gevorderd niveau te krijgen, zou ik nog deze constraints toevoegen:
sql

ALTER TABLE reviews
ADD CONSTRAINT chk_rating
CHECK (rating BETWEEN 1 AND 5);

sql

ALTER TABLE tickets
ADD CONSTRAINT chk_ticket_price
CHECK (price >= 0);

sql

ALTER TABLE tickets
ADD CONSTRAINT chk_ticket_quantity
CHECK (quantity_sold <= quantity_total);

sql

ALTER TABLE order_items
ADD CONSTRAINT chk_order_quantity
CHECK (quantity > 0);

Deze zorgen ervoor dat je database verkeerde gegevens automatisch weigert.
